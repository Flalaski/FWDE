# Decision Log

| Date | Decision | Rationale |
|------|----------|-----------|
| 2026-11-02 | All window facts live in one registry (`_WinReg` / `_WinRegSnapshot`); every predicate is a view over it | Measured per-call Win32 costs (style ~0.03µs, `IsWindowVisible` ~0.03µs, DWM ~0.82µs, `GetWindowRect` ~1.9µs) versus what the code did: `GetVisibleWindows` ran `IsWindowValid` → `IsOwnedInteractivePopup` → `_IsSelfWindow` → `IsWindowFloating`, each re-reading title/class/process/style/ex-style/rect, and `IsFullscreenWindow` alone made ~9 calls plus three array allocations. That is ~35 calls per candidate window per 250ms cycle. The registry classifies once, caches on a cheap signature (style/ex-style first, then rect), a 1s TTL and a Config generation counter, and publishes a per-tick snapshot with a movable-handle set so the O(n²) force loop does no Win32 work. Result: UWS 3254→696µs, GVW 3146→645µs, CDL 2900→576µs. |
| 2026-11-02 | Physics energy is scored from ACHIEVABLE displacement, not raw velocity | Live profiling showed 96–99% of ticks in `chaos` for minutes with 0 moves in 66% of one-second samples and energy frozen at exactly 0.1567 across 61 samples, with 11 force-settles in 179s that never converged. Energy summed `vx²+vy²` for every tracked window, but `CalculateWindowForces` clamps the target to the work area and `ApplyWindowMovements` refuses to move active/locked/snapping bodies — a body pinned at an edge therefore regenerated force forever, and chaos held the force multiplier at 0.6 permanently. Scoring the clamped target delta (and excluding bodies AWM skips) makes "energy" mean "motion the visual layer can actually produce": chaos fell to 0%, energy to 0.0007, and the settle/watchdog machinery stops thrashing. |
| 2026-11-02 | Added a provable idle gate instead of lowering the tick rate | Measured from the live build: CDL 2900µs → 576µs after the registry work, but a settled layout still burned ~1ms/tick computing forces that AWM would never apply. A settled layout is a pure-function no-op: same positions + same state ⇒ same ~zero forces. The gate skips the pipeline when every tracked window's real rect matches our state (±2px), nothing is dragging/menuing/snapping, the tracked set is unchanged and energy is below `(1.5/0.45)²` per window — AWM's own move threshold and max non-drag smoothing alpha. `ApplyWindowMovements`' resync sets `_layoutDirty` so a user nudge wakes the engine within one tick. Verified live: idle at 64Hz, woke to 105 moves/s on a nudge, settled back to idle. |
| 2026-11-02 | Tick period default changed 16ms → 15ms (64Hz), with the quantization table documented | Measured in an isolated AHK v2 process, with and without `timeBeginPeriod(1)` (no difference): 1–15ms → 15.71ms (64Hz), 16ms → 25.16ms (40Hz), 17–30ms → 31.59ms (32Hz), 33ms → 47.63ms (21Hz). AHK v2 runs ONE Win32 timer (`SLEEP_INTERVAL` 10ms) and polls script timers against `GetTickCount()`, whose 15.625ms granularity means a 16ms request sits 0.375ms above a tick boundary and splits into a bimodal one-tick/two-tick mix (0.4·15.625 + 0.6·31.25 ≈ 25.0ms). 16 was therefore the single worst value to request: the "~60Hz" comment described a cadence the platform never delivered. |
| 2026-11-02 | `SWP_ASYNCWINDOWPOS` enabled by default, with two-deep command history in the movement pass | Synchronous `SetWindowPos` blocks the animation thread on the slowest managed app's message pump (documented rationale for the flag; measured 10–20× faster async). Because the request is *posted*, the return value means "accepted", not "applied", and the rect can lag one command. AWM therefore keeps `prevPositions` alongside `lastPositions` and treats a rect matching the previous command as a pending application rather than an external move — which would otherwise zero momentum and set `_layoutDirty` every frame. |
| 2026-11-02 | Shell AppBars and DWM-cloaked windows are excluded from the body set | RetroBar (a taskbar replacement) was pinned by the shell to the band it reserves yet tracked as a physics body, so it accumulated force it could never spend. `IsShellAppBarWindow` matches the exact reserved band between monitor edge and work area — self-verifying, since the band has zero thickness when no AppBar is registered (verified precise against the live desktop, zero false positives). DWM-cloaked windows (closed UWP frames, windows on other virtual desktops) keep `WS_VISIBLE` but are not on screen, so they are rejected via `DwmGetWindowAttribute(DWMWA_CLOAKED)` in the same classification pass. |
| 2026-11-02 | Fixed infinite self-relaunch loop in `RunAsAdmin` self-elevation; relaunch is now one-shot | `_IsElevated()` opened the process token with TOKEN_ADJUST_DEFAULT (0x0020) instead of TOKEN_QUERY (0x0008). `OpenProcessToken` succeeds with 0x20 but `GetTokenInformation(TokenElevation)` fails, so the function returned false even in an elevated process. Once `RunAsAdmin` defaulted to true this became an infinite relaunch loop (each instance relaunched "elevated" and exited). Fixed the access right and added `_ElevationAttempted()` — the relaunch passes `--fwde-elevated`, and a process started with that marker never relaunches again, so a future detection failure cannot loop. |
| 2026-11-02 | Adopted the user's tuned Parameter Settings as the new built-in defaults (13 values) and audited the whole parameter surface | Screenshot-driven retune: `Damping` 0.216→0.1429, `ManualRepulsionMultiplier` 1→15, `PairSmallWindowBoost` 3→0.5, `RepulsionImpulseScale` 4.32→6.92, `ResizeDelay` 20→1, `RunAsAdmin` false→true, `SeedDiagonalMaxSteps` 18→50, `SeedDiagonalStep` 61→200, `SeedJitterRange` 31→100, `SmallWindowReferenceDim` 1200→507, `SmallWindowThresholdW` 614→507, `SmallWindowThresholdH` 591→504, `UserMoveTimeout` 523→50. Audit fixes: removed dead params (`ManualGapBonus`, `NoiseScale`, `NoiseInfluence`, `ManualWindowColor`) and the stale `ManualWindowAlpha` range override; added `DesktopIconPhysics` to the boolean spec list (it was skipped by the Number gate, so it never appeared in the settings GUI); expanded ranges so retuned defaults are not pinned to slider bounds; added a default-in-range guard, load-time clamping, descriptions for all 50 params, and the alphabetical spec ordering the runtime/saved config already used. |
| 2026-08-05 | DAW main windows AND their plugin/FX windows are now tracked; only tiny utility chrome floats | REAPER's main window (`REAPERwnd` / `reaper.exe`) showed as "Untracked Floating" — FWDE never managed REAPER. Root cause: `reaper.exe` was blanket-listed in `ForceFloatProcesses`, so `IsWindowFloating` step 1 floated EVERY window from that process (same latent issue for ableton/flstudio/cubase/studioone/bitwig/protools). After fixing the main window, its floating `VST:`/`JS:` FX windows (`#32770` dialogs) were still floated via `IsPluginWindow`/title patterns — and floating windows receive NO physics (`ResolveFloatingCollisions` only runs on the tracked `g["Windows"]`), so plugins were completely ignored. Fix: step 1's DAW branch now tracks ALL DAW windows except tiny utility chrome. New helpers: `_IsDAWProcess()` (DAW process list, synced with `ForceFloatProcesses`) and `IsTinyUtilityWindow()` (<40×40 px, or class `RPTopmostButton`) — REAPER's 16×16 `tb` pin buttons overlay each FX window, and tracking them would let repulsion rip them off their host. Non-DAW `ForceFloatProcesses` entries (cmd/conhost/WindowsTerminal) unchanged. |
| 2026-08-01 | Steam windows are now manageable (not fullscreen, not floated) | Research confirmed: Steam's UI lives in CEF `steamwebhelper.exe` processes and its windows use class `SDL_app` with Steam's custom chrome. Two misclassifications hid Steam from FWDE: (1) `IsFullscreenWindow` treats `SDL_app` as a fullscreen-game class and had `steamwebhelper.exe` in `fullscreenProcesses` → Steam flagged `invalid:fullscreen` (even the "About Steam" dialog!); (2) `IsWindowFloating` rule 7 would float it (WS_POPUP, no WS_CAPTION — custom title bar). Fix: added `steam.exe`/`steamwebhelper.exe` to `manageableProcesses` in `IsFullscreenWindow` (removed from `fullscreenProcesses`), and added them to the default `ForceTrackProcesses` config so the SDL_app/custom-chrome window is never floated. The popup-cohesion check still runs first, so true Steam popups/dialogs are handled normally. |
| 2026-08-01 | Elevated-window (UIPI) handling: precise exclusion reasons + opt-in self-elevation | Steam (`steamwebhelper.exe`), Notepad++ [Administrator], and elevated FileZilla were all "invalid" (never tracked). Root cause: those windows run ELEVATED while FWDE runs non-elevated — Windows UIPI makes style/minmax queries throw "Access is denied" and blocks SetWindowPos, so IsWindowValid rejects them. Fix: (1) `_GetWindowExcludeReason()` reports the precise reason in Ctrl+Alt+D (invalid:minimized/maximized/toolwindow/not-visible/no-title/fullscreen/access-denied-elevated); (2) new opt-in config `RunAsAdmin` — when enabled and FWDE isn't elevated, FWDE relaunches itself elevated at startup (Run '*RunAs'), which is the only way to manage elevated windows. Debug output shows a NOTE when elevated windows are present. |
| 2026-08-01 | WS_POPUP only floats when the window has NO caption; added "why not tracked" debug section | `FloatStyles` (0x80000000 = WS_POPUP) floated ANY popup-styled window. AHK v1 GUIs (`AutoHotkeyGUI`, e.g. Ahk2Exe) and custom-chrome apps (Steam) are created with WS_POPUP + WS_CAPTION → looked like normal windows but were floated → FWDE never moved them. Fix: rule 7 in `IsWindowFloating` now requires `!(style & 0x00C00000)` (no WS_CAPTION) for the WS_POPUP float; caption'd custom-chrome windows are managed. True caption-less popups/overlays still float (and are handled by popup/companion cohesion). Debug output (Ctrl+Alt+D) now lists untracked non-floating windows with the exact reason: owned-popup / fwde-self / companion / invalid / monitor-filter. |
| 2026-08-01 | WM_MOVE/WM_SIZE no longer mark windows "active" unless the user is actually dragging; added idle-physics diagnostic | Self-moving apps (DarkTide launcher realigning its decorate layer) generate WM_MOVE constantly. WindowMoveHandler/WindowSizeHandler refreshed `g["ActiveWindow"]`/`g["LastUserMove"]` on EVERY such message → the app's window became permanently "active" → frozen by active-window protection → physics produced energy (overlap/edge forces) but 0 moves, settle fired forever. Fix: only refresh ActiveWindow/LastUserMove and auto-lock (ManualLock) when `GetKeyState("LButton","P")` is held (real user drag/resize). Position sync on app-initiated moves is retained. Added `_DiagnoseIdlePhysics()` — when energy is elevated but 0 moves for ~1s, logs each tracked window's skip reason (minmax/popup-freeze/active/manual-lock/snap/resync/at-target/should-move) to FWDE_debug.log. |
| 2026-08-01 | Implemented Same-App Companion Cohesion for decorate/overlay layers (e.g. Warhammer 40K DarkTide launcher) | The DarkTide launcher splits its UI into a main window + a decorative overlay as TWO top-level WPF `HwndWrapper[launcher.exe;;…]` windows from the same process. FWDE tracked both independently → pushed the decorate layer off its main window. Fix: `AreCompanionPair` (same process + same WPF `HwndWrapper` family + partial overlap with LOW floor so already-drifted layers still pair + similar size; generic fallback requires an overlay-style window, i.e. WS_POPUP without WS_CAPTION, to avoid gluing unrelated stacked windows), `ScanCompanionWindows` groups connected components and picks the largest window as anchor, `SyncCompanionWindows` lockstep-follows. NO host freeze (layer is permanent, unlike popups). Config: `CompanionFollowEnabled`, `CompanionScanIntervalMs`, `CompanionMinOverlap`, `CompanionMaxSizeRatio`. Also factored self-window detection into shared `_IsSelfWindow()`. |
| 2026-08-01 | Implemented Owned-Popup Cohesion subsystem for browser permission bubbles ("Chrome Legacy Window") | Chrome renders permission prompts ("Allow access to location?", notifications, camera/mic) as SEPARATE OS-level owned popup windows. FWDE tracked them as independent physics bodies → physics fought Chrome's own anchoring → popup sat at a stale offset → clicks on its buttons missed. Fix (3 mechanisms): (1) `IsOwnedInteractivePopup()` detection (GW_OWNER + class/title/style heuristics, system-chrome + self-process exclusion), (2) `ScanOwnedPopups()` registry (popup→owner) with exclusion from independent physics in `GetVisibleWindows`, (3) `SyncOwnedPopups()` lockstep — re-applies the owner's exact movement delta every tick (covers physics, user drags, external moves) — plus `_popupOwners` host freeze in all movement paths so popup buttons stay clickable. Config: `PopupFollowEnabled`, `PopupFreezeHost`, `PopupScanIntervalMs`. Also excludes FWDE's own GUI windows (parameter settings) from physics management. |
| 2026-07-12 | Implemented multi-pass chain-effect collision resolution (5 passes with diminishing weights) | Single-pass collision resolution only propagated forces to direct neighbors. Multi-pass with probed positions allows velocity accumulated in pass 1 (A→B) to cascade to pass 2 (B→C), creating realistic chain reactions through window clusters. Pass weights: 0.40, 0.25, 0.17, 0.10, 0.08 for controlled total force. |
| 2026-07-12 | Expanded all parameter slider ranges 2-5x and added missing parameter overrides | Many parameters were at their max (RepulsionForce=5 capped at 5, PairSeparationBase=0.08 capped at 0.08, etc.) preventing further tuning. All ranges significantly expanded: RepulsionForce 0.01-20, PairSeparationBase 0.001-0.5, RepulsionImpulseScale 0.01-10, MaxSpeed 0.5-120, NoiseScale 100-20000, etc. Added overrides for previously uncovered params: SeedDiagonalStep, NoiseScale, NoiseInfluence, ManualWindowAlpha, etc. |
| 2026-07-12 | Wired Config["Damping"] into all physics loop damping factors; user config values adopted as new defaults | Previously hardcoded damping factors (0.994, 0.998, 0.99, 0.98, 0.95, 0.88) ignored the Config["Damping"] parameter. Now all damping uses Config["Damping"] with a slight electron-app boost. New defaults reflect user's tuned config: higher repulsion (5.0), zero damping (1.0), ultra-fast visual step (1ms), generous overlap tolerance (50). |
| 2025-08-02 | Redesigned FWDE physics system from center-attraction to overlap-based repulsion | The original center-attraction system was too forceful and noticeable. The new system only acts when windows actually overlap or are too close, providing gentle separation forces. This creates a more natural, subtle experience where windows maintain their positions unless there's a real need to adjust them. Also added user move detection to temporarily pause physics when someone manually positions a window. |
